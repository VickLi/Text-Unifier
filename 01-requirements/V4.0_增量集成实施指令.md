# V4.0 增量集成实施指令

> **目标**: 将已完成的 V4.0 代码从"全量 bug 修复"模式切换为"逐功能线增量验证"模式
> **受众**: AI 架构师 → 输出程序员可执行的逐步骤指令
> **原则**: 不改架构、最小侵入、每步可验证、每步可回退

---

## 一、背景

V4.0 经过 7 轮修订、23 个 Bug 修复。Bug 反复出现的根因是：所有 12 个模块一次性开发完成，十几个组件互相交叉依赖，修 A 模块的 Bug 触发 B 模块的新 Bug，排查范围过大。

## 二、策略：功能线增量集成

按依赖关系将 12 个模块拆为 **1 个共享基础设施 + 3 条功能线**，严格执行阶段顺序：

```
阶段 0（共享基础设施）：A. 文件输入 + B. 归一化/编码探测
         ↓
阶段 1a（最短独立线）：I. 文档对比           ← 先做，做完前 1b 和阶段 2 不得启用
         ↓
阶段 1b（核心功能线）：B. 合并算法 + D. 预览区 + C. 连接点 + L. 阈值
         ↓
阶段 2（导出线）：J. 导出
```

```text
阶段 1a 完成前：阶段 1b 的 mergeCore flag 和阶段 2 的 export flag 必须保持 false。
阶段 1a 标记 stable 后 → 方可启用阶段 1b。
阶段 1b 标记 stable 后 → 方可启用阶段 2（导出）。

注意：模块 E(内容清洗)、M(搜索替换)、H(撤回栈) 已从本软件移除，
移到独立项目「Text Unifier 内容工具」中实现。
```

每条线做完都是一个**独立可用的完整功能**。上游线验证通过后，下游线出 Bug 只需排查"刚解锁的模块"。

## 三、模块依赖总览

```
                        阶段 0：共享基础设施

                    │  A. 文件输入（芯片栏） │
                    │  B. 归一化/编码探测    │
                    │  （所有线的前置依赖）   │
                    └──────────┬───────────┘
                               │
              ┌────────────────┴────────────────┐
              │                                 │
    阶段 1a：文档对比                   阶段 1b：合并去重核心
    ┌──────────────────────┐          ┌──────────────────────┐
    │ I. 文档对比           │          │ B. 合并算法（重叠匹配）│
    │ （3 模块，最短独立线） │          │ D. 预览区（连续文本）  │
    │ 可并行于 1b           │          │ C. 连接点列表          │
    └──────────┬───────────┘          │ L. 合并阈值设置        │
               │                      │ （5 模块，依赖 1a 完成）│
               │                      └──────────┬───────────┘
               │                                 │
               └──────────────┬──────────────────┘
                              │
                        阶段 2：导出
              ┌─────────────────────────────────┐
              │ J. 导出（UTF-8 .txt）            │
              │ （1 模块，依赖 1a 或 1b 的预览区） │
              └─────────────────────────────────┘

**已移除模块（移至独立项目「Text Unifier 内容工具」）**：
- E. 内容清洗（繁简/全角转换）
- M. 搜索替换（Ctrl+H）
- H. 撤回栈（5 步 FIFO）
```

**依赖规则**：
- 阶段 1a 与 1b 互不依赖（可并行开发，但需 1a 先验证启用）
- 阶段 2（导出）需要一个有内容的预览区 → 依赖 1a 或 1b 完成
- E/M/H 已移除，不再作为本软件功能

## 四、实现方式：Feature Flag（不改架构）

### 4.1 在 Store 中添加功能开关

文件: `src/store/useStore.ts`

```typescript
interface AppState {
  // ... 现有字段 ...

  // === 功能开关（增量集成用，全部稳定后可移除） ===
  // 启用顺序：阶段 1a → 阶段 1b → 阶段 2
  featureFlags: {
    // 阶段 1a：文档对比（最先启用）
    diffViewer: boolean;

    // 阶段 1b：合并去重核心（1a stable 后方可启用）
    mergeCore: boolean;

    // 阶段 2：导出（1b stable 后方可启用）
    exportFeature: boolean;
  };
}
```

初始状态：
```typescript
featureFlags: {
  diffViewer: false,     // 阶段 1a：第 1 个启用
  mergeCore: false,      // 阶段 1b：1a stable 后启用
  exportFeature: false,  // 阶段 2：1b stable 后启用
}
```

### 4.2 各组件渲染时检查 Flag

组件不改内部逻辑，仅在最外层包裹条件渲染：

```tsx
// 示例：DiffViewer 的渲染
const { featureFlags } = useStore();

// 模式切换 Tab
{featureFlags.diffViewer && (
  <button onClick={() => setMode('compare')}>📋 文档对比</button>
)}

// 对比视图
{activeMode === 'compare' && featureFlags.diffViewer && (
  <DiffViewer />
)}
```

同样的模式应用于：CleanPanel, SearchReplace, ExportButton, UndoRedoButtons, ConnectionPointList 等。

未被启用的功能区域显示**灰色占位块**（非空白），标注功能名称，便于开发者确认 Flag 生效：

```tsx
{!featureFlags.mergeCore && (
  <div className="w-[260px] bg-gray-100 rounded border border-dashed border-gray-300 
                  flex items-center justify-center text-gray-400 text-sm">
    合并去重（未启用）
  </div>
)}
```

## 六、程序员执行规范

### 6.1 每个步骤必须做的事

1. **只改当前步骤涉及的 flag 和组件**，不碰无关文件
2. **修改后启动软件验证**，对照"验证标准"列逐条确认
3. **通过后立即 Git commit**，commit message 格式：`step 2.2.3: search highlight works`
4. **未通过则回退**，排查范围仅限本步骤修改的文件

### 6.2 禁止行为

- ❌ 一次改多个 flag
- ❌ 跳过验证步骤直接进入下一步
- ❌ "顺便修一下"无关的 UI 细节（另开分支）
- ❌ 修改 store 的核心逻辑（如撤回、合并算法）而不跑对应验证

### 6.3 出 Bug 时排查流程

```
1. 本步骤改了哪些文件？ → 只检查这些文件
2. 上一步同样功能是否正常？ → 正常说明本步骤引入的 Bug
3. 回退本步骤修改 → 重新实现
```
